# Create an approval policy without copying UIDs or hashes

A policy records **your approved correction**, not an automatically discovered fix. The generator reads the live target and namespace, copies their UIDs, hashes the exact current template/spec and creates a short-lived private JSON file. It never changes the cluster or enables opt-in.

The target must already have the required approved opt-in annotation and must not have a previous attempt latch, recognized GitOps ownership or a namespace pause. Start with a separately approved lab workload, not the repository's Argo-managed platform application. See [repair boundaries](automatic-repair.md).

## 1. Provide only the intended correction

Copy one matching example into a private location and edit it:

| Action | Approved JSON input | Repair command |
| --- | --- | --- |
| `images` | [Container names → compatible image digests](../examples/approved-images.json) | `watch-recovery` or `recover` |
| `containers` | [Named approved container fields](../examples/approved-container.json) | `repair` |
| `selector` | [Intended Service label selector](../examples/approved-selector.json) | `repair` |
| `replicas` | [Approved replica count](../examples/approved-replicas.json) | `repair` |

Examples are templates, not approvals for your application. Replace container names, labels, paths and image placeholders with verified values. Image policies must list all regular containers and use real compatible digest references. Replica policies only restore a nonzero count upward, at most 10, with no HPA ownership. Probe corrections must restore known correct behavior rather than hide application failures. Plaintext environment values are refused.

## 2. Generate from the live target

For image recovery:

```bash
mkdir -p reports
# approved-images.local.json is YOUR reviewed input; it is not generated by this command.
devops-toolkit policy create --context YOUR_CONTEXT --namespace platform \
  --kind Deployment --name YOUR_DEPLOYMENT --action images \
  --approved approved-images.local.json --expires-in 20 \
  --output reports/recovery-policy.local.json
```

For an approved Service selector correction:

```bash
devops-toolkit policy create --context YOUR_CONTEXT --namespace platform \
  --kind Service --name YOUR_SERVICE --action selector \
  --approved approved-selector.local.json --output reports/selector-policy.local.json
```

Use `--kind Deployment --action containers` or `--action replicas` for the other cases. Expiry defaults to 20 minutes, allowed 5..60. The output parent must exist and the file must be new. File mode is 0600. The current spec must actually differ from the approved correction. API access failure, invalid input, missing opt-in, pause, identity change, previous attempt or incompatible action refuses generation.

A generated policy authorizes that exact observed state. A later spec/template change needs new review and a newly generated policy; do not replace hashes to bypass a refusal. Image and container repair still require an observed failed rollout before execution. Generating a policy does not wait for or cause that failure.

## 3. Check it offline, then preview

```bash
devops-toolkit policy check reports/recovery-policy.local.json
devops-toolkit recover --policy reports/recovery-policy.local.json
```

`policy check` verifies schema and expiry only. It does not contact Kubernetes, check current identity, establish permissions or approve the fix. A recovery preview can refuse while a rollout is progressing; use `watch-recovery` to wait for the approved failure signal.

After reviewing the policy, unattended execution is explicit:

```bash
devops-toolkit watch-recovery --policy reports/recovery-policy.local.json \
  --execute --audit reports/recovery-UNIQUE-ID.jsonl
```

For the other actions, use `repair` with the matching generated policy. Preview is the default; no policy is enabled just by creating it. See [emergency stop and permissions](operations.md).

Exit codes: `0` valid/generated, `2` refusal/error. Generation and offline validation do not perform cluster mutations or send alerts.

You can additionally run [repair-dry-run](dry-run.md) to ask Kubernetes to validate the approved correction without persisting a patch. It does not replace the live checks or failed-rollout conditions required for actual execution.
